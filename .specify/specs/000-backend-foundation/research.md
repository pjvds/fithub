# Research: 000-backend-foundation

> Generated by speckit-plan Phase 0 — consolidates all resolved technical decisions with rationale and alternatives considered.

---

## R1: Runtime Platform

**Decision:** Cloudflare Workers (TypeScript)

**Rationale:**
- Edge-first execution model gives global low-latency by default
- Workers + D1 + Queues + R2 + Durable Objects form a cohesive serverless stack with no cold-start penalty
- Durable Objects provide per-user state isolation without external coordination services
- Cost-effective at hobby/MVP scale; pay-per-request pricing

**Alternatives Considered:**
- AWS Lambda + DynamoDB: Mature but cold starts, more complex IAC, higher baseline cost
- Vercel Edge Functions: Limited compute primitives (no queues, no durable state)
- Fly.io: Good DX but requires container management; less integrated primitives

---

## R2: Infrastructure-as-Code Framework

**Decision:** SST v3 (Ion) with Cloudflare provider

**Rationale:**
- SST v3 has first-class Cloudflare support (Workers, D1, KV, Queues, R2, DO)
- Resource linking (`Resource.Bucket`, `Resource.Queue`, etc.) provides type-safe bindings
- Single `sst.config.ts` for all infrastructure; `sst dev` for local iteration
- Active development by SST team; growing Cloudflare ecosystem

**Alternatives Considered:**
- Raw Wrangler: No IaC; manual config per binding; no multi-resource orchestration
- Pulumi: Overkill for single-provider stack; more boilerplate
- Terraform + CF provider: HCL syntax overhead; less TypeScript-native DX

---

## R3: Database

**Decision:** Cloudflare D1 (SQLite-based)

**Rationale:**
- Native to Workers runtime — zero-latency binding, no network hop
- SQLite semantics: ACID transactions within a single batch, JSON1 functions
- Generous free tier; sufficient for MVP activity volumes
- Drizzle ORM provides typed schema + migrations

**Alternatives Considered:**
- Turso (LibSQL): Compatible but adds external dependency and latency
- PlanetScale: MySQL-based; more setup; connection pooling needed from Workers
- Supabase (Postgres): Full RDBMS but overkill; connection overhead from edge

---

## R4: Authentication Strategy

**Decision:** OpenAuth.js via SST Auth

**Rationale:**
- SST Auth wraps OpenAuth.js with resource linking; single `sst.config.ts` declaration
- Supports Apple Sign-In, Google Sign-In, email magic link out of the box
- Issues JWTs validated by `api` Worker middleware — no session store needed
- Runs as a Cloudflare Worker (same platform as rest of stack)

**Alternatives Considered:**
- Clerk: Proprietary; vendor lock-in; monthly fees
- Auth0: Heavy SDK; external network call per auth check
- Custom JWT: High implementation effort; security risk
- Lucia Auth: Good library but less SST integration than OpenAuth.js

## R5: Event Bus Topology (AD-5)

**Decision:** D1 transactional outbox → Cloudflare Queues

**Rationale:**
- Cloudflare's documented best practice for guaranteed DB↔bus consistency
- Atomic: `db.batch([stateWrite, outboxInsert])` ensures no event loss
- Outbox Relay Worker (Cron ~5s) drains pending rows to Queues
- Decouples producers from consumers — adapters don't call downstream directly
- No external infrastructure (Kafka, RabbitMQ) needed

**Alternatives Considered:**
- Side-channel events (dual-write): No atomicity guarantee on D1 (no LISTEN/NOTIFY)
- Event sourcing: Feasible on Cloudflare but painful (no managed event store, expensive replays)
- Hybrid DB write + best-effort publish: Loses events under failure
- Direct Queues publish (no outbox): Loses events if Queue is temporarily unavailable

---

## R6: Event Schema Standard (AD-5)

**Decision:** CloudEvents v1.0 JSON

**Rationale:**
- CNCF-standard wire format; avoids future migration
- Required attributes (`specversion`, `id`, `source`, `type`, `time`) provide consistent metadata across all events
- Zod schemas validate `data` payload per event type at both publish and consume boundaries
- Events ≤4 KB JSON including envelope

**Alternatives Considered:**
- Typed JSON + Zod (no CloudEvents envelope): Simpler but non-standard; loses interop
- Protobuf: Binary format; overkill for ≤4 KB payloads; poor D1 JSON1 compat
- Avro: Schema registry overhead; not warranted at this scale

---

## R7: Delivery & Idempotency (AD-5)

**Decision:** At-least-once delivery + consumer-side idempotency keys with bounded-window cleanup

**Rationale:**
- Cloudflare Queues provides at-least-once delivery natively
- Consumers check `processed_events(consumer_id, event_id)` before handling
- Bounded-window cleanup: daily cron deletes rows older than 24h
- **Safety invariant:** cleanup window (24h) > Queues max retry window (12h) — no message can be re-delivered after its dedup row is cleaned up
- Extended outage (>12h): messages go to DLQ, not lost; DLQ replay re-introduces with original `event_id`

**Alternatives Considered:**
- Exactly-once semantics: Not supported by Queues; would require Durable Objects per consumer (expensive)
- No idempotency (fire-and-forget): Duplicate processing on retry; unacceptable for activity creation
- Global event store dedup: Expensive; grows unbounded; overkill for consumer-side concern

---

## R8: Outbox Retention (AD-5)

**Decision:** Mark `processed_at` timestamp; retain rows indefinitely (no automated sweep for MVP)

**Rationale:**
- Retained outbox rows serve as audit trail and replay source
- Automated sweep deferred to post-MVP to reduce initial complexity
- D1 storage costs are minimal for metadata-only rows (events ≤4 KB)
- Future sweep can be added as Cron job when table size becomes a concern

**Alternatives Considered:**
- Delete after enqueue: Loses audit trail; prevents replay
- TTL-based expiry: D1 has no native TTL; would require custom sweep (deferred)
- Move to cold storage: Premature optimization for MVP

---

## R9: Event Scope (AD-5)

**Decision:** Domain events only — emit when another service or the user must react

**Rationale:**
- Guiding principle: "If only the owning Worker cares, don't emit"
- Reduces bus traffic and consumer complexity
- Internal mechanics (token refresh success, retry attempts) stay local
- Exception: `token.refresh_failed` and `connection.degraded` ARE domain events because other services and users need to react

**Canonical Event Catalogue (10 events):**

| Event Type | Emitter | Subscribers |
|---|---|---|
| `activity.ingested` | Platform Adapters | Dedup Engine |
| `activity.created` | Dedup Engine | Push Notifier, Activity Store |
| `activity.merged` | Dedup Engine | Push Notifier, Activity Store |
| `connection.created` | Auth Worker | Sync Orchestrator |
| `connection.revoked` | Auth Worker / API | Sync Orchestrator, Push Notifier |
| `connection.degraded` | OAuth Token Vault | Push Notifier, Sync Orchestrator |
| `health_upload.received` | API Gateway | Dedup Engine |
| `sync_job.completed` | Sync Orchestrator | Push Notifier |
| `sync_job.failed` | Sync Orchestrator | Push Notifier, Alerting |
| `token.refresh_failed` | OAuth Token Vault | Connection Manager, Push Notifier |

**Explicitly NOT emitted (internal):** `token.refreshed`, `sync_job.retrying`, `activity.dedup_skipped`, `cache.invalidated`

**Alternatives Considered:**
- Emit everything (including internal): High bus traffic; consumers must filter; noise
- Emit nothing (RPC only): Tight coupling; no async processing; hard to add new consumers

## R10: Blob Storage (AD-5)

**Decision:** Cloudflare R2 with path-only references in events

**Rationale:**
- R2 is S3-compatible, zero egress fees, native to Workers
- Path convention: `users/<user_id>/activities/<activity_id>/<artifact>` (e.g., `activity.fit`, `raw_strava.json`)
- Events reference blobs by **path only** — never URLs, bucket names, or provider URIs
- SST `Resource.Bucket.get(path)` naturally enforces path-only convention
- Storage-backend independence: path works regardless of R2 bucket name or region

**Alternatives Considered:**
- Store raw payloads in D1: Row size limits; expensive for binary data; bloats backups
- Store raw payloads inline in events: Exceeds 4 KB event limit for FIT/TCX files
- S3 (AWS): External dependency; egress fees; cross-provider latency

## R11: API Framework

**Decision:** Hono (on Cloudflare Workers)

**Rationale:**
- Ultra-lightweight; built for edge runtimes
- First-class Cloudflare Workers support
- Middleware pattern for auth, CORS, logging
- Type-safe route parameters with Zod validation

**Alternatives Considered:**
- itty-router: Simpler but less middleware ecosystem
- Express.js: Not designed for edge; requires node compat mode
- tRPC: Good for full-stack TypeScript but overkill for mobile API

---

## R12: Mobile Framework

**Decision:** Flutter

**Rationale:**
- Single codebase for iOS and Android
- Strong HealthKit/Health Connect integration via packages
- Dart's type system fits well with typed API contracts
- Team familiarity / preference

**Alternatives Considered:**
- React Native: Viable but less performant for health data access
- Native (Swift + Kotlin): Maximum platform integration but double development effort
- Kotlin Multiplatform: Emerging; less mature UI story

---

## R13: Per-User Ordering

**Decision:** Durable Objects (one per user)

**Rationale:**
- Cloudflare Queues does not guarantee ordering
- DO provides single-threaded execution per user — natural serialization point
- Already used for sync coordination (cursors, locks, pending dedup)
- No global ordering needed; per-user ordering sufficient for activity consistency

**Alternatives Considered:**
- Queue partitioning by user: Not supported by Cloudflare Queues
- Optimistic locking in D1: Race conditions under concurrent sync jobs
- External coordination (Redis): Adds latency and external dependency
