# Research: 005-web-frontend

> Generated by speckit-plan Phase 0 — consolidates all resolved technical decisions with rationale and alternatives considered.

---

## R1: Web Framework

**Decision:** Astro ^4 (static-first, island architecture, Cloudflare Pages adapter)

**Rationale:**
- Static-first rendering keeps Core Web Vitals strong without sacrificing interactivity; the dashboard only needs thin islands (SyncNowButton, ConnectionCard status badge, dedup resolution controls)
- Island granularity means only components that need JS hydrate; the rest is zero-JS HTML — ideal for a data-display dashboard
- Official Cloudflare Pages adapter runs at the edge inside the same SST project; no separate deployment target
- Pivot decision locked 2026-05-06 (see `.specify/memory/tech-stack.md` §Web Frontend)

**Alternatives Considered:**
- Next.js: heavier runtime, larger default JS bundle, more complex edge config
- SvelteKit: excellent choice, but Astro integrates more naturally with the zero-JS-first philosophy for this use-case
- Remix: good routing model but no native Cloudflare static export; overkill for a mostly-read dashboard

## R2: Styling

**Decision:** Tailwind CSS ^4

**Rationale:**
- Utility-first keeps CSS co-located with markup; no separate stylesheet to maintain
- Built-in responsive utilities cover desktop + mobile viewports without media query boilerplate
- Tailwind v4's CSS-first config is lighter than v3's JS config; works seamlessly with Astro's Vite pipeline
- No significant alternative evaluated — Tailwind is the default per the spec assumption; any change would require spec amendment

**Alternatives Considered:**
- CSS Modules: more verbose, requires naming conventions, harder to refactor across components
- Vanilla Extract: type-safe but heavy for a thin client; better suited for a design-system package

---

## R3: Session Strategy

**Decision:** `HttpOnly`, `Secure`, `SameSite=Lax` cookie set by the Auth Worker on the apex domain (`fithub.space`)

**Rationale:**
- `HttpOnly` prevents XSS from reading the session token; no JS token management needed
- `SameSite=Lax` protects against CSRF for state-mutating requests while allowing navigation redirects
- Apex-scoped cookie allows `app.fithub.space` and `auth.fithub.space` to share the session without cross-origin fetch complexity
- Zero fitness tokens ever touch `localStorage` or `sessionStorage` — hard requirement per Constitution §1

**Alternatives Considered:**
- Bearer token in memory + periodic refresh: breaks on hard reload; requires persistent JS state machinery
- `localStorage` token: XSS-vulnerable; explicitly rejected by Constitution §1

## R4: API Client Strategy

**Decision:** Hand-written `fetch` wrapper at `web/src/lib/api-client.ts` using response types from `packages/core`

**Rationale:**
- Shared types from `@fithub/core` mean a backend breaking change produces a TypeScript compile error in the web app before runtime
- Thin wrapper stays transparent and easy to test; no third-party HTTP client dependency to track
- Wrapper adds: retry on transient 5xx (max 2 retries, 500ms/1500ms backoff), `x-correlation-id` header forwarding, and typed `ApiError` normalisation
- Same pattern used by the backend's internal modules

**Alternatives Considered:**
- Generated SDK from OpenAPI spec: adds tooling complexity; types would diverge from Core types over time
- Axios: unnecessary dependency; native `fetch` + retry wrapper is simpler and has no bundle cost

## R5: Mocking Strategy for Development/Testing

**Decision:** Mock Service Worker (MSW ^2)

**Rationale:**
- Single set of MSW handlers works in both the Vite dev server (browser) and Vitest (Node); no duplicated mock setup
- Intercepts at the `fetch` layer so the API client under test is exercised identically to production
- Fixtures are TypeScript-typed against `packages/core` response types — caught by compiler if contract drifts

**Alternatives Considered:**
- json-server: extra process to manage; harder to keep in sync with shared types
- Hard-coded fixtures in components: pollutes production code; removes type safety

---

## R6: End-to-End Test Tooling

**Decision:** Playwright ^1.4x against the deployed preview environment (no MSW in E2E)

**Rationale:**
- E2E tests exercise the real network stack; no mocks at this layer
- Playwright's cross-browser coverage (Chromium, Firefox, WebKit) satisfies AC-9 (latest 2 major versions of Chrome, Firefox, Safari, Edge)
- Cloudflare Pages preview deployments provide a stable URL per branch for E2E to target

**Alternatives Considered:**
- Cypress: heavier, slower CI, worse cross-browser support in headless mode
- WebdriverIO: more config overhead; Playwright's API is cleaner for Astro's SSR pages

---

## R7: Performance Budget Enforcement

**Decision:** Lighthouse CI (`@lhci/cli`) in GitHub Actions; enforce Performance ≥90 and Best Practices ≥90 on the authenticated dashboard route

**Rationale:**
- Constitution §5 requires performance regression tests in CI
- Lighthouse reflects real user metrics (LCP, TBT, CLS) that matter for the dashboard experience
- CI budget enforcement prevents gradual regression without manual review overhead

**Alternatives Considered:**
- Bundle size check only: misses runtime perf (render-blocking, layout shifts)
- Manual Lighthouse runs: unreliable; no enforcement

---

## R8: Structured Logging

**Decision:** Astro server endpoints import `@fithub/core/logging`; client-side errors are posted to `POST /api/errors`

**Rationale:**
- Constitution §8 requires all services to emit structured logs — symmetrically applies to the web's server layer
- A shared `ErrorCode` enum lets browser-side errors be mapped to typed codes before sending
- Astro middleware attaches `correlationId` and a scoped logger to every server request; no bare `console.*` in server code

**Alternatives Considered:**
- Sentry: third-party dependency; Constitution's zero-tracker stance for v1 rules it out
- Plain `console.error` in server endpoints: violates Constitution §8 directly

---

## R9: SST Integration

**Decision:** `sst.cloudflare.StaticSite` resource in `sst.config.ts` pointing to `web/` build output, attached to `app.fithub.space`

**Rationale:**
- Colocating the web site in the SST project gives it typed resource bindings and a single deploy pipeline
- `StaticSite` handles the Cloudflare Pages deployment; Astro's Cloudflare adapter produces the correct output
- `sst dev` serves the Astro app locally alongside the Workers

**Alternatives Considered:**
- Separate Pages project outside SST: loses typed bindings; splits CI/CD
- Cloudflare Pages via GitHub integration (not SST): loses `sst dev` integration and per-stage environments
